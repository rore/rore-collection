# Collection coordination

When the user asks about team handoff, fresh manager/developer sessions, or replacing the team—including whether to do so or whether a handoff guide exists—read [Team handoff](references/team-handoff.md) before answering. Discussion authorizes assessment only; executing the transfer requires approval of the exact roster. A request for a handoff prompt alone does not authorize creating chats.

1. State the outcome, acceptance evidence, constraints, and allowed delegation budget. Reuse existing authoritative work. Split only where a result can be verified independently; record prerequisites and shared-resource conflicts.
2. When Minimap is available, designate one owner-managed shared roadmap checkout per repository using it; inspect that checkout and preserve unrelated dirty changes. The lead updates sequence and status on accepted assignments, progress, blockers, and verified completion. A sole developer makes those updates itself. Workers use isolated checkouts and report the exact feature reference, revision, evidence, and blockers. Without Minimap, use the existing authoritative issue, file, or task record.
3. When the user has established a team or task owner, prefer a suitable existing collaborator before spawning a replacement. Create another agent when no suitable collaborator exists, capacity is unavailable, or independent review is needed. Old sessions alone do not constitute an established team. Ask candidate sessions about their current work. Idle state, participant membership, and an empty work-reference list do not prove availability. Prefer Relay for independent sessions when available. For fallback, verify that the recipient's current state and the authorized channel allow an offer without interrupting ongoing work; otherwise defer and report the limitation. Use native delegation for subagents. Send a bounded offer with the full scope, prerequisites, acceptance evidence, and one requested response: `accept`, `defer`, or `decline`. Preserve the recipient's model and effort unless the user asks to change them. Existing user assignments take precedence.
   When adding a member to an established role-based team, resolve the intended session type, model/effort, authorized Relay name, and mapped guide using existing team instructions and the [role skill](../persistent-agent-roles/SKILL.md). Include name and guide adoption in normal assignment acceptance; disclose missing setup rather than treating the member as ready.

4. Treat a saved, delivered, or waking Relay message as transport evidence only. An explicit `accept` starts an assignment; reviewed evidence establishes completion. Keep uncertain or blocked delivery visible in the canonical work source. At natural coordination checkpoints, inspect accepted unfinished work using current status and available delivery evidence; investigate apparent stalls and surface concrete blockers. Do not infer failure from silence, poll frequently, preempt, promise an automatic wake, blindly resend, or dispatch the same work to another agent after a timeout. Exception to non-interruption: for urgent stop, cancellation, or scope corrections, do not treat queued delivery as applied. If waiting could let the worker take an unwanted action, use an authorized interrupting fallback, preserving its model and effort. Confirm the worker adopted the correction; otherwise clearly tell the human it remains unconfirmed.
   For an authorized recurring completion watch, define what it awaits and its stop condition. If no operation is running and progress requires a human decision, surface that decision once and pause the watch. Bounded observation periods follow their agreed end condition instead.

5. The receiver follows its repository's applicable gates. If blocked, promptly report to the lead what is blocked, the next required action, and who needs to act. Apply blockers and stop conditions only to the work they govern. Continue independent authorized work unless the blocker also prevents it. The lead handles manager or developer actions within existing authority and surfaces human decisions directly to the human. Update the same authoritative source when the blocker clears.

   In repositories that use persistent roles, load the [role skill](../persistent-agent-roles/SKILL.md) at handoff. Carry the mapping and guide path/revision, plus unpublished edits, in the existing continuation packet; the successor resolves its current Relay name and reads current guidance before accepting unfinished work.

   When a dependency clears, use an authorized continuation mechanism that can resume the waiting worker; a message alone may not restart an idle subagent. Verify once that it accepted the continuation and resumed; if stale state blocks progress, use an authorized fallback under the channel rules above.

   Check existing authorization before requesting human approval. When approval is needed, report the approval requirement and designate one requester; the lead must clearly surface the specific decision needed and where the human must approve, including any worker-local prompt. Share the exact approval source with the implementer and verify work resumes; message delivery is not approval.

   For assigned implementation, investigation, testing, or substantive review of an existing roadmap item, follow the owning tool's association procedure when supported; casual browsing and clerical edits do not qualify. In normal acceptance, resume, handoff, cancellation, and completion updates, the lead checks that the canonical item reflects current work and the worker confirms session participation matches its current assignment under Pallium's lifecycle guidance when available. Require successful tool evidence for attachment or detachment, including removal when the assignment ends while the feature remains unfinished. Report unavailable or limited integration and continue ordinary work; no separate checklist or confirmation exchange is required. Never invent a reference or attach on the receiver's behalf. Acceptance may accompany starting work after applicable gates; no extra lead confirmation is needed unless scope or dependencies changed. For handoff, the new receiver accepts before starting.
6. Before accepting a result, reconcile it with the latest authorized requirements known to the lead, including updates sent but not yet confirmed received. Surface material departures from user requirements or established core product behavior for explicit human review and approval under Agent Workflow's behavioral-integrity guidance when available, otherwise the repository's native process; passing individual assignments does not approve a departure in the combined result. Consolidate missing changes before another review; do not expect workers to know undelivered instructions. Review each reported revision and the combined outcome before closing work. If a worker cannot send its result through an authorized channel, leave it in its final response for the lead to retrieve and review through supported task-reading tools; do not retry or reroute around an approval denial. A worker's final response is not assignment completion: if the objective remains unfinished, establish and act on the next continuation, dependency, approval, or user decision.

   When repeated attempts fail or recovery work expands without advancing the user's outcome, reassess the approach before assigning another patch. Separate required outcomes and safety guarantees from implementation choices. Consider whether an existing or supported approach can replace the accumulated machinery. Choose the next action for its expected progress or useful evidence, not merely because it fixes the latest failure. Briefly explain any change of direction to the human; request approval only if it exceeds existing authorization. This is a response to actual drift, not a new document, checkpoint, or review after every patch.

   Carry the task through already-authorized merge and delivery steps once required gates pass; do not invent an extra approval stop or treat existing approval as permission for new scope. At completion, have the worker report task-worktree cleanup or why it must be retained, following the repository or host cleanup procedure. Communicate substantive results, blockers, or decisions; reuse reliable evidence and existing records instead of ACK/status ping-pong. Record current state, pending offers, decisions, evidence, and the next action in the authoritative source so a fresh coordinator can resume. History may supply context but does not replace current state.

Load Minimap's, Agent Workflow's, or Pallium's installed skill only when using that tool's procedures. If Agent Workflow is absent, follow the repository's native gates. If Pallium is absent, use an authorized channel only when the same no-interruption check passes; otherwise report the limitation. Do not claim participant evidence. None of the three tools is required to perform ordinary work. Do not create a scheduler, parallel registry, or copied roadmap state.

During real use, note confusing instructions, unnecessary exchanges, missed coordination, and user corrections. Report only new, actionable problems; consolidate duplicates and omit routine progress or successful coordination summaries. At completion or a meaningful blocker, present that feedback to the human and also send it to a feedback recipient designated in local instructions, if any, through an authorized channel using the same no-interruption check above. State what was expected, what happened, its impact, and the smallest suggested improvement; distinguish instruction gaps from tool failures. Reuse existing evidence, omit sensitive details, and avoid separate feedback logs or routine "no issues" reports. If forwarding is unavailable, tell the human; do not hold up the work.
