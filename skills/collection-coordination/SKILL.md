# Collection coordination

For a user-requested manager/team session replacement, load [Team handoff](references/team-handoff.md). Carry out the transfer, asking only for material missing information; a request for a handoff prompt alone does not authorize creating chats.

1. State the outcome, acceptance evidence, constraints, and allowed delegation budget. Reuse existing authoritative work. Split only where a result can be verified independently; record prerequisites and shared-resource conflicts.
2. When Minimap is available, designate one owner-managed shared roadmap checkout per repository using it; inspect that checkout and preserve unrelated dirty changes. The lead updates sequence and status on accepted assignments, progress, blockers, and verified completion. A sole developer makes those updates itself. Workers use isolated checkouts and report the exact feature reference, revision, evidence, and blockers. Without Minimap, use the existing authoritative issue, file, or task record.
3. Ask candidate sessions about their current work. Idle state, participant membership, and an empty work-reference list do not prove availability. Prefer Relay for independent sessions when available. For fallback, verify that the recipient's current state and the authorized channel allow an offer without interrupting ongoing work; otherwise defer and report the limitation. Use native delegation for subagents. Send a bounded offer with the full scope, prerequisites, acceptance evidence, and one requested response: `accept`, `defer`, or `decline`. Preserve the recipient's model and effort unless the user asks to change them. Existing user assignments take precedence.
4. Treat a saved, delivered, or waking Relay message as transport evidence only. An explicit `accept` starts an assignment; reviewed evidence establishes completion. Keep uncertain or blocked delivery visible in the canonical work source. At natural coordination checkpoints, inspect accepted unfinished work using current status and available delivery evidence; investigate apparent stalls and surface concrete blockers. Do not infer failure from silence, poll frequently, preempt, promise an automatic wake, blindly resend, or dispatch the same work to another agent after a timeout. Exception to non-interruption: for urgent stop, cancellation, or scope corrections, do not treat queued delivery as applied. If waiting could let the worker take an unwanted action, use an authorized interrupting fallback, preserving its model and effort. Confirm the worker adopted the correction; otherwise clearly tell the human it remains unconfirmed.
5. The receiver follows its repository's applicable gates. Check existing authorization before requesting human approval. If blocked, promptly report the exact action and approval requirement to the lead, and continue independent authorized work where possible. Designate one requester; the lead must clearly surface what is blocked, the specific decision needed, and where the human must approve, including any worker-local prompt. Share the exact approval source with the implementer and verify work resumes; message delivery is not approval. On accepted applicable work, follow the owning tool's association procedure for an exact reference when supported; if unavailable or limited, report that and do not claim participant evidence. Never invent a reference or attach on the receiver's behalf. Acceptance may accompany starting work after applicable gates; no extra lead confirmation is needed unless scope or dependencies changed. For handoff, the new receiver accepts before starting; the departing worker removes only its own finished explicit association after leaving.
6. Before accepting a result, reconcile it with the latest authorized requirements known to the lead, including updates sent but not yet confirmed received. Consolidate missing changes before another review; do not expect workers to know undelivered instructions. Review each reported revision and the combined outcome before closing work. A worker's final response is not assignment completion: if the objective remains unfinished, establish and act on the next continuation, dependency, approval, or user decision. When repeated attempts fail or recovery work expands without advancing the user's outcome, reassess the approach before assigning another patch. Separate required outcomes and safety guarantees from implementation choices. Consider whether an existing or supported approach can replace the accumulated machinery. Choose the next action for its expected progress or useful evidence, not merely because it fixes the latest failure. Briefly explain any change of direction to the human; request approval only if it exceeds existing authorization. This is a response to actual drift, not a new document, checkpoint, or review after every patch. Carry the task through already-authorized merge and delivery steps once required gates pass; do not invent an extra approval stop or treat existing approval as permission for new scope. Communicate substantive results, blockers, or decisions; reuse reliable evidence and existing records instead of ACK/status ping-pong. Record current state, pending offers, decisions, evidence, and the next action in the authoritative source so a fresh coordinator can resume. History may supply context but does not replace current state.

Load Minimap's, Agent Workflow's, or Pallium's installed skill only when using that tool's procedures. If Agent Workflow is absent, follow the repository's native gates. If Pallium is absent, use an authorized channel only when the same no-interruption check passes; otherwise report the limitation. Do not claim participant evidence. None of the three tools is required to perform ordinary work. Do not create a scheduler, parallel registry, or copied roadmap state.

During real use, note confusing instructions, unnecessary exchanges, missed coordination, and user corrections. Report only new, actionable problems; consolidate duplicates and omit routine progress or successful coordination summaries. At completion or a meaningful blocker, present that feedback to the human and also send it to a feedback recipient designated in local instructions, if any, through an authorized channel using the same no-interruption check above. State what was expected, what happened, its impact, and the smallest suggested improvement; distinguish instruction gaps from tool failures. Reuse existing evidence, omit sensitive details, and avoid separate feedback logs or routine "no issues" reports. If forwarding is unavailable, tell the human; do not hold up the work.
